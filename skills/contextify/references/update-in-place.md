# Update in place

Purpose: the managed-block contract that lets contextify refresh a context file without destroying what a human wrote around it.

## The managed-block contract

- Markers are single-line HTML comments, chosen so every reader ignores them: `<!-- contextify:begin v1 -->` and `<!-- contextify:end -->`. Source: DECISIONS.md D5.
- The header is the line right after the begin marker: `<!-- Generated by contextify {toolVersion}; writer={generatedBy}; at={generatedAt}; commit={commit}; regenerate: /contextify update -->`.
- The footer is the last managed line, plain text rather than a comment, so a human reading the rendered file actually sees it: `verified on {date} against {commit}`.
- A file carries exactly zero or one complete marker pair. Source: D5, D7.

## Conflicts: refuse, and name the lines

Three conflict shapes, each refused rather than guessed at, each named by line number in the refusal:

- An unpaired marker, a begin with no matching end, or the reverse.
- A nested pair, a begin found while a block is already open.
- A duplicate pair, two complete begin/end pairs in the same file.

An edited managed block, meaning its digest no longer matches the stamp, is also a conflict: the run stops and asks rather than overwriting a human's in-block edit. `--yes` does not bypass this conflict, and does not bypass the 150-line ceiling either. Source: D5, D7, D8.

## What survives untouched

Every byte outside the managed block, including line endings, is preserved exactly. The header and footer are rewritten only when the bytes between them actually change, so a no-op re-run is byte-identical: no mtime churn, no timestamp drift for its own sake. Source: D5, D7.

## A human file with no markers

Propose insertion as a diff; never silently adopt the file as generated content. Insert the block after the first H1, or at the top when there is none. Report `migration pending` until a human approves the insertion. Source: D7.

## Migrating instructions that already exist elsewhere

Generic instructions already living in another agent file, a `.cursorrules`, `.github/copilot-instructions.md`, or an old hand-written `CLAUDE.md`, get migrated explicitly into AGENTS.md, with the diff shown to the human, never silently absorbed. Until that migration happens, the other file is not yet a thin pointer, and the run reports it as such rather than treating it as already done. Source: D7.

## What `update` actually does

`update` re-reads only the evidence that moved since the last stamp, and revises only the AGENTS.md lines that evidence supports; it does not regenerate the whole file from scratch. A full diff is always shown before anything is written, in every mode that writes. Source: D8, D3.

## The bounded mistakes log

`.contextify/mistakes.md` is optional and is never created automatically. If a human creates it, it stays bounded: at most 60 lines, newest entry first, oldest entries pruned on write. `update` reads it, but only offers to promote an entry into a rule once the same pattern has appeared in more than one entry, never on the first occurrence, and the promoted rule keeps a reference back to the incidents in evidence. The log itself is never imported into any context file; it is an evidence store, not context. Source: D18.
